== THE INCIDENT (root-caused, fixed, closed) ==
Symptom: doctor showed 13 VPN'd services "NOT attached to gluetun". Investigation (docker inspect, NOT
trusting doctor) found: last night's `up` recreated gluetun with a NEW container ID; compose left the 13
`network_mode: container:` dependents pinned to the OLD, now-dead gluetun netns. They lost egress ENTIRELY
(sealed, not leaking — the dead netns had no route; confirmed via in-container trace). Ghost-detach.

Root cause class: `network_mode: service:gluetun` is FAIL-OPEN. Compose does not recreate netns dependents
when only the namespace-host (gluetun) changes. Any gluetun recreate that doesn't cascade to its
dependents orphans them. Hit THREE times this session: (1) the original v5.5.0-era `up`, (2) the update
path, (3) trash-sync's bare `docker compose run recyclarr`.

Remediation that day: scoped `docker compose up -d --force-recreate --no-deps <13 services>` re-pinned them
to the live gluetun. leak-test green.

== OLIVETIN FRONT DOOR — investigation + partial build (the big second-half thread) ==
GOAL: a web UI of buttons/dropdowns over mediastack.sh's safe verbs (update, enable/disable, vpn toggle,
wire, doctor/status/leak-test), so Nick can drive the stack from a browser/phone. QOL, zero new capability.

WHY OliveTin (researched, current as of this session): purpose-built "safe front door over your CLI" —
Go binary, tiny, FOSS, actively maintained. Its OWN security guidance MATCHES our design (non-root/
container, narrow sudo to only the needed script, auth, reverse proxy). Alternatives rejected: Semaphore/
Rundeck/AWX (fleet/Ansible platforms — overkill, wrong model); Portainer/Dockge (drive raw compose ->
BYPASS the guard -> disqualified); Cockpit (host admin, complements but doesn't run our verbs); Homepage
(read-only dashboard — good future pairing for status tiles + service blurbs, safe because read-only).

ARCHITECTURE (decided, docs-verified):
  - OliveTin runs as an UNPRIVILEGED CONTAINER in the stack (no docker.sock, not privileged, not root).
  - It reaches the host via SSH-TO-HOST (OliveTin's OWN documented preferred pattern; image ships an ssh
    client). Use the MANUAL ssh setup (host-key checking ON), NOT the "easy" one (which disables it).
  - Two independent narrowings + the CI audit guard the path to root:
      #1 forced-command SSH key: authorized_keys pins command="/usr/local/bin/olivetin-frontdoor". That
         wrapper whitelists verbs, rejects ALL shell metacharacters, then calls mediastack.sh via sudo.
         WRAPPER LOGIC PROVEN IN SANDBOX: every allowed verb runs; every attack (;, &&, |, $(), ``, >,
         path traversal, quoted-spaces, off-whitelist verbs) rejected.
      #2 narrow sudoers: host `olivetin` user may `sudo` ONLY mediastack.sh.
      #3 mediastack.sh itself is injection-free (front-door audit) and re-validates every service arg.
  - Dropdowns are ENTITY-BACKED (OliveTin reads a JSON file; my earlier `choicesCommand` was FICTIONAL —
    corrected via docs). A cron/startup OliveTin action refreshes the entity file via `ssh ... list <subset>
    --json` (that's why list + list --json were built and shipped). enable->list disabled, disable->list
    enabled, vpn->list vpntoggle, wire->list wire.
  - AUTH (interim): OliveTin's BUILT-IN local-user auth, ON, even on LAN (the panel can change the stack,
    so it's higher-stakes than the media services). Real SSO (Authelia/Keycloak) is future hardening.
  - REACHABILITY: Traefik route like other services (LAN). NOT public. WAN only via deliberate portforward.
  - PASSWORD: frontdoor-install will PROMPT interactively at install time and hash via OliveTin's argon2
    helper. Deliberately NOT via mediastack.sh set-credentials — a password must never flow through the
    front-door-exposed script's argv. set-credentials stays for media-service creds only.

SECURITY AUDIT OF mediastack.sh (done, clean): no eval; every service arg whitelisted via svc_exists
(exact grep -qx) + label checks; NO user input reaches any `sh -c` (all static single-quoted); container
names quoted. Verdict: SAFE to expose via narrow sudo. The CI tripwire (scripts/audit-frontdoor-safety.sh,
in lint.yml) now ENFORCES the two properties (no eval, no interpolating sh -c) so a regression fails CI.
See docs/frontdoor-safety.md for the full contract (incl. host-side reqs the audit can't check).

DELIBERATELY NOT EXPOSED via front door: set-credentials, traefik-setup, new-service, invite, configure,
install, uninstall (free-text/config), and logs (follows -f, would hang the action).
